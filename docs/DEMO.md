# Hosting a Public Demo

You can host a public demo deployment of Finance Manager where visitors explore the app with sample data that resets daily. The demo is a normal Coolify app with two additions on top of the standard prod setup.

## Setup

### 1. Create a second Coolify app

Point it at this repo with `docker-compose.prod.yml` as the compose file — same as the regular prod deployment.

### 2. Create a Postgres resource and wire it up

Provision a Postgres resource in Coolify (or reuse an existing one) **dedicated to the demo**. The reset job wipes this database every night, so it must not be shared with anything else.

On your new app, set these environment variables. The `DB_*` values come from the Postgres resource's connection details — copy them exactly (the default `DB_NAME` in the codebase is `finance_manager`, but your Postgres resource may have created a database with a different name; use whatever the resource panel shows):

```
DB_HOST=<from your Postgres resource>
DB_PORT=5432
DB_USER=<from your Postgres resource>
DB_PASSWORD=<from your Postgres resource>
DB_NAME=<from your Postgres resource>
API_SECRET=<random secret>
REACT_APP_API_SECRET=<same value as API_SECRET>
FINANCE_MANAGER_DEMO_MODE=true
FINANCE_MANAGER_TELLER_INTEGRATION_ENABLED=false
```

Deploy the app once. The `backend-migrate` service will run Alembic to create the tables. The demo backend will start, but the database is still empty — visitors landing on the URL right now would see a blank app. The next step seeds it.

### 3. Add the daily reset as a Coolify scheduled task

The reset job runs **inside the existing `backend` container** via `docker exec`, so it inherits the container's environment automatically — no need to re-declare DB credentials or the demo flag.

In the Coolify UI for the demo app:

1. Open the application's page and click the **Scheduled Tasks** tab in the left navigation.
2. Click **+ Add** (or **New Scheduled Task**).
3. Fill in the fields:

   | Field         | Value                                                                     |
   | ------------- | ------------------------------------------------------------------------- |
   | **Name**      | `demo-daily-reset` (anything descriptive)                                 |
   | **Container** | `backend` — the service to exec inside                                    |
   | **Command**   | `uv run python -m app.demo.reset`                                         |
   | **Frequency** | `0 9 * * *` (daily at 09:00 UTC; pick an off-peak hour for your audience) |

4. Click **Save**.

### 4. Seed the database for the first time

After saving the scheduled task, click **Run Now** on it (the icon next to the task in the scheduled-tasks list). This triggers an immediate run. Watch the task's logs — you should see:

```
demo reset: shifted N days; inserted 2 users, 3 sources, 579 transactions, 5 accounts
```

If you see `refusing to run: demo mode is not enabled`, double-check that `FINANCE_MANAGER_DEMO_MODE=true` is set on the `backend` service and that you redeployed after adding it.

Visit your demo URL — the dashboard, transactions, and net-worth pages should now have data, and the blue banner should be visible at the top of every page.

### 5. Daily resets after that

The scheduled task takes over from here. Every night at the configured time it wipes the demo database and reseeds from the fixture, with all dates shifted so the latest transaction is dated today.

## What the demo does

- Loads ~580 hand-curated transactions for two users (Alice & Ben) over 24 months.
- Every reset shifts all dates so the latest transaction is "today" — filters like "last 30 days" never show empty data.
- Visitors can freely edit, delete, mark transfers, build dashboards. The daily reset wipes their changes and reseeds.
- The frontend shows a permanent banner at the top of every page indicating demo mode is active, with a link to this repo.

## Safety

The reset script refuses to run unless `FINANCE_MANAGER_DEMO_MODE=true` is set in its environment. Pointing it at a non-demo database without that flag will cause it to exit non-zero without touching the data — this protects you from a misconfigured scheduled task wiping a real instance.

## Regenerating the fixture

The demo dataset lives at `backend/app/demo/fixture.json` and is generated by `backend/app/demo/build_fixture.py`. If you want to change the curated content (add transactions, tweak categories, change users), edit the builder and re-run:

```bash
cd backend
uv run python -m app.demo.build_fixture
```

Commit the regenerated `fixture.json` alongside the builder changes. The next scheduled-job run on the demo deployment will pick up the new content. To roll out the change immediately, click **Run Now** on the scheduled task.

## Troubleshooting

**`FATAL: database "finance_manager" does not exist`** — your `DB_NAME` env var doesn't match the database name Coolify created on the Postgres resource. Open the Postgres resource panel in Coolify and copy the actual database name into `DB_NAME` on the app. Alternatively, `CREATE DATABASE finance_manager;` on the Postgres resource and leave `DB_NAME=finance_manager`.

**`refusing to run: demo mode is not enabled`** — the scheduled task can see the backend container but the container doesn't have `FINANCE_MANAGER_DEMO_MODE=true`. Add it to the app's env vars and redeploy.

**Scheduled task runs but the banner doesn't show** — the frontend reads `/api/demo/config` once at page load. Hard-refresh the page (Cmd/Ctrl + Shift + R) to pick up the new config. If still not showing, check the browser network tab for the `/api/demo/config` response.

**Latest transaction not on today** — check the scheduled task's log for the `demo reset: shifted N days` line. If `N` is 0 and the latest transaction is still old, the task ran against a different database than the backend (mismatch between `DB_NAME` on the task and on the backend — but since they share env vars when running as a scheduled task, this should be impossible; verify the task is set to **Container: backend**, not a separate one-off container).
